### 1. 语法与编译校验

> **首轮开发时**沙箱为 Linux 且无法联网获取 .NET 8 SDK，真实编译**未在本地完成**，只做了降级到 `net6.0` 的语法检查。
> **2026-09-16 已在 Windows 上补齐真实编译与测试**，结果如下（SDK 10.0.301，目标框架 `net8.0-windows10.0.18362.0`）。

`dotnet build ZzzAutoSign.sln -c Release` 首轮报 4 个错误，修复后又暴露 4 个，共 **8 个真实缺陷**，现已全部修复：

| # | 缺陷 | 位置 | 说明 |
|---|---|---|---|
| 1 | 通知包命名空间写错 | `Notify/ToastNotifier.cs`、`Program.cs` | 写的是 `Microsoft.Toolkit.Uwp.Notifications`，但 `CommunityToolkit.WinUI.Notifications` 7.1.2 导出的命名空间是 `CommunityToolkit.WinUI.Notifications`（该包从未导出过旧名） |
| 2 | 目标框架少写 Windows 版本 | `ZzzAutoSign.csproj`、`ZzzAutoSign.Tests.csproj` | `net8.0-windows` 会让 NuGet 选中包里的 `lib/net5.0` **精简版**（只有 `ToastContentBuilder`，没有 `Show()`、没有 `ToastNotificationManagerCompat`）。改成 `net8.0-windows10.0.18362.0` 才解析得到 `lib/net5.0-windows10.0.18362` |
| 3 | 调用了不存在的 API | `Program.cs` | `ToastNotificationManagerCompat` 只有 `CreateToastNotifier` / `Uninstall` / `OnActivated`，没有 `SetCurrentAppUserModelId`。改为 P/Invoke 调用 shell32 的 `SetCurrentProcessExplicitAppUserModelID`，AUMID 仍取 `AppPaths.AppUserModelId`，与开始菜单快捷方式保持一致 |
| 4 | `Timer` 类型歧义 | `Core/ProcessWatcher.cs` | 同时引用了 WinForms 与 System.Threading，裸写 `Timer` 产生 CS0104。已显式限定为 `System.Threading.Timer` |
| 5 | 重复的常量模式 | `MiHoYo/Models/ZzzRetCode.cs` | switch 里 `-100 => …` 与 `NotLoggedIn`（值也是 `-100`）重复，触发 CS8510「模式不可访问」。删掉重复分支 |
| 6 | Playwright API 已变更 | `CredentialGrabber/PlaywrightGrabber.cs` | 1.47 起 `CookiesAsync` 返回 `IReadOnlyList<BrowserContextCookiesResult>`，不再是 `Cookie[]` |
| 7 | `_` 被当成了 int 参数 | `tests/AtomicFileTests.cs` | `Select(_ => …)` 里的 `_` 是 int 形参，内层 `_ = 读取结果` 于是变成「把 Sample 赋给 int」。外层改回显式数组循环 |
| 8 | 并发读写下 `File.Replace` 必失败 | `Config/AtomicFile.cs` | 读侧原先用 `File.ReadAllText`（`FileShare.Read`），会让写侧的 `File.Replace` 撞上共享冲突并抛 `IOException`。改为以 `FileShare.ReadWrite \| FileShare.Delete` 打开，替换另外加了有限次退避重试 |

**测试结果**：`dotnet test` —— **55 个用例全部通过**（修复前 54 通过 / 1 失败，失败的就是上面第 8 条暴露出来的并发用例）。

### 最关键的未知项

**`act-nap-api.mihoyo.com` 接受哪套签名组合？**

这是整个项目最大的不确定性。方案里内置了三种签名模式的**自动轮换**：遇到 `retcode = -1` 时会自动从 `WebDs1 → AppDs1 → X6Ds2` 依次尝试，并把成功的模式写回配置。

所以**这个不确定性已经被代码消化掉了**，你不需要手动排查。若三种都失败，日志里会有明确记录，此时按 [接口说明](../docs/接口说明.md) 第 7 节自行抓包更新 `endpoints.json` 即可。

## 三、开发环境说明

首轮开发在 Linux 沙箱中完成，当时：

- **无法在沙箱内编译**：目标框架 `net8.0-windows` + WinForms + WMI 均为 Windows 专属；沙箱只有 .NET 6 SDK 且无法联网安装 .NET 8
- **无法产出 Windows exe**：交叉编译 WinForms 不可行

因此首轮的交付形式是**源码 + GitHub Actions 工作流**，把真正的编译与打包交给 `windows-latest`。

**该限制现已解除**：项目已在 Windows + .NET 8 上真正编译、测试并发布（见第一节第 1、5 小节），
不再依赖云端才能验证构建。CI 保留，用于保证「推上去就能复现」。

### 如何构建

推送到 GitHub 后：

```bash
# 方式一：自动构建（每次 push 都会跑）
git push origin main
# 到 Actions 页面下载 artifact

# 方式二：打 tag 出正式 Release
git tag -a v1.0.0 -m "发布说明写在这里"
git push origin v1.0.0
# Actions 会直接发布正式 Release（非 draft），含两个 zip + SHA256SUMS

```

## 四、架构决策备忘

记录几个「为什么不那样做」的决定，便于后续维护时理解。

| 决策 | 原因 |
|---|---|
| 不做账号密码自动登录 | 米哈游通行证密码登录强制极验（Geetest）行为验证码，纯 HTTP 无法通过。绕过方案要么需要把密码发送给第三方打码平台，要么需常驻自动化浏览器且容易触发风控。两者都不可接受 |
| 用 WMI 事件而非轮询 | 轮询有延迟（用户能感知到）且持续占用 CPU；WMI 事件是即时且零开销的 |
| 单文件自包含而非依赖框架 | 用户不需要预装 .NET 运行时，降低使用门槛 |
| DPAPI 而非明文配置 | Cookie 等同于登录态，明文存放风险过高。DPAPI 保证只有当前用户能解密 |
| 凭证单独存而非放 settings.json | 职责分离：`settings.json` 可以随便分享给别人看，`credential.bin` 不行 |
| 风控错误不重试 | 重试「需要验证码」这类错误只会加重风控，可能触发账号临时限制 |
| salt 做成运行时可配置 | 官方升级客户端会更换 salt，做成可配置后用户不必等新版本程序 |
| 全部成功才记录「今日完成」 | 部分角色失败时，下次启动游戏应继续尝试，不能因为一个角色成功就跳过其余角色 |
